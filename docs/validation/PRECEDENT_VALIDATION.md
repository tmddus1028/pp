## 로컬 LLM 실호출 — 한국 0844 사건, 청구항 1

설정: Ollama 0.40.3, `qwen3:14b`, `LOCAL_LLM_THINK=false`, context 40,960, 출력 12,000,
재요청 1회, `IMPROVEMENT_PRUNE_INVALID=true`. 입력 context 약 22,000자.

| 시도 | 결과 | 원인 / 조치 |
| --- | --- | --- |
| 1 | 근거 검증 실패 (108초) | 청구항 PDF 줄바꿈("부\n여하고")으로 요소 문자열 불일치 → 공백 무시 비교 |
| 2 | 응답 중단 | 출력 6,000토큰 한도 → 12,000으로 설정화 |
| 3 | 근거 검증 실패 (134초) | 요소 비교에 `CLAIM-1` 누락 → 원문에 있는 요소만 해당 청구항 ID 자동 보충 |
| 4 | **검증 통과, status=abstained (124초)** | 6개 구성요소 × 심사관 인용 위치 매핑 성공. 개선 전략은 명세서 인용 게이트 미통과로 모두 제외 |

해석: 14B 로컬 모델은 "심사관 주장 정리"까지는 근거와 함께 해내지만, 명세서 원문을 정확히 인용해야 하는
보정 전략은 아직 못 만듭니다. Claude API(`IMPROVEMENT_PROVIDER=anthropic`)로 같은 사건을 다시 기록해야 합니다.

### s165 서버 (RTX 3090 ×2) 32B

- 서버 Ollama는 0.24.0. 기존 `orcarouter/Qwen3.8-27B-Uncensored`는 `unknown model architecture: 'qwen35'`로 실행 불가.
- 공식 `qwen3:32b`(20GB)를 받아 SSH 터널(`ssh -N -L 11435:127.0.0.1:11434 s165`)로 연결. 코드의 loopback 제한은 그대로.
- 0.24.0은 스키마의 큰 반복 한도(maxLength 4000)를 문법으로 바꾸지 못해 500 오류
  (`number of repetitions exceeds sane defaults`). Ollama에 보내는 스키마에서만 상한을 빼도록 수정
  (`grammar_schema`), 응답은 Pydantic이 상한까지 다시 검증.

## LLM 채점표 (`data/eval/kr/`)

모델에는 첫 의견제출통지서와 당시 청구항만 주고, 실제 대응·결과로 채점합니다. 채점 대상 사건은 대응 사례 DB에서 제외합니다.

| 사건 | 실패한 대응 → 결과 | 성공한 대응 → 결과 | 자료 |
| --- | --- | --- | --- |
| 0844 | 행사 기간·지역 기반 설정 등 서비스 수준 한정 → 거절결정 | 단말 해상도·NFC 구비여부로 쿠폰 형식 결정 등 기술 수단 → 등록 | 의견서 2건(OPD 수동) + API |
| 0874 | "데이터 서비스 설정 상태 인식" → 거절결정 | 접속망 확인 → 차단 여부 판단 → 과금/비과금 구분 → 등록 | API만 |

두 사건 모두 추상적 한정은 실패, 구체적 판단 단계·기술 수단 추가는 성공. 채점 항목은 Claude가 쓴 초안이라
팀(가능하면 변리사·멘토) 검토가 필요합니다. "거절결정 → 재심사 → 등록" 사건은 의견서 없이 API만으로 채점표를 만들 수 있습니다.

### 추가로 확인된 KIPRIS 기능

- `ClaimsChangeHistoryService/amendmentHistoryDetailInfo`: 보정마다 청구항 전문 + `<Ins>`/`<Del>` 변경 표시 → 보정서 원문·등록공보 대체.
- `IntermediateDocumentRGService/amendmentInfo`: 등록결정 시 직권보정 내역.
- 심판사항: `http://plus.kipris.or.kr/kipo-api/kipi/judgmentInfoSearchService/<op>?...&ServiceKey=` (다른 4개와 주소·파라미터가 다름).
  0948은 거절결정불복심판 2019원2316, 심결문 있음.
- 의견제출통지서 `advancedSearchInfo?sendDate=YYYYMMDD`: 발송일별 출원번호 목록(2019-04-09 하루 862건) → 출원번호 공급 문제 해결.

## 한국 대응 사례 (KIPRIS Plus API, 2026-10-19)

키: `.env`의 `KIPRIS_ACCESS_KEY`(또는 기존 이름 `REST_AccessKey`). 신청 서비스 5개 중 4개를 사용합니다.

| 서비스 | REST 이름 | 사용 오퍼레이션 |
| --- | --- | --- |
| 의견제출통지서 | `IntermediateDocumentOPService` | `advancedSearchInfo`, `examineResultInfo`(거절이유 표) |
| 거절결정서 | `IntermediateDocumentREService` | `advancedSearchInfo`(PDF 주소), `examineResultInfo`(미해소 표), `rejectDecisionInfo`(대응 서류) |
| 등록결정서 | `IntermediateDocumentRGService` | `bibliographicInfo`, `contentInfo`(재심사 경유 여부) |
| 청구항 변동 이력 | `ClaimsChangeHistoryService` | `amendmentHistoryInfo`(보정서 제출일) |
| 심판사항 | 미사용 | 서비스명 미확인 |

`patUtiModInfoSearchSevice`(서지 상세)는 신청하지 않은 서비스라 `resultCode 31 DEADLINE_HAS_EXPIRED_ERROR`가 납니다.
표는 `행§`, `셀†` 구분자로 옵니다. 응답은 `data/kipris_cache/`에 캐시하고, 서비스별 월 950회에서 멈춥니다.

**재설계안 전제 확인 — 거절결정서에 미해소 사유가 명시되는가**: 55개 출원의 거절결정 33건 중
무대응 11건을 뺀 22건에서 **18건(82%)이 "거절이유가 해소되지 않은 부분과 관련 법조항" 표를 구조화 필드로 제공**했습니다.
나머지 4건은 표가 없어 사유별 라벨에서 제외합니다. → 한국도 사유 단위 해소 라벨이 대부분 가능합니다.

추가 발견:
- 거절결정서 본문에 **출원인 의견서 요지와 심사관 판단**이 사유별로 정리돼 있습니다(OPD CAPTCHA 없이 확보).
  형식이 제각각이라(`라. 의견서에 대한 검토`, `N-1. 의견 내용 / N-2. 의견 내용 검토`, `2. 의견서를 통한 출원인의 주장`, 제목 없는 본문)
  제목 키워드 + 본문 대체 규칙으로 추출합니다. 사유별 라벨이 붙은 거절결정 행 24개 중 20개에서 주장을 추출했습니다.
- **무대응 거절결정**("지정기간 … 의견서 또는 보정서 제출이 없었으며") 20건은 실패가 아니라 제외합니다.
  처음 버전은 이를 "해소"로 잘못 셌습니다(무대응 결정서에는 미해소 표가 없음).

| 유형 | 라벨 | 해소 | 보정 포함 (해소/전체) | 주장만 |
| --- | --- | --- | --- | --- |
| 신규성 | 12 | 100% | 11/11 | 1/1 |
| 진보성 | 54 | 50% | 26/51 | 0/1 |

제외: 무대응 20, 재심사 경유 11, 미해소 표 없음 4. 대응 방식 미확인 22(다음 조치가 재통지·등록이고 보정서 기록이 없는 경우).
표본 출원은 5개 공식 샘플 + 2015년 의견제출통지서 샘플 앞 50개라 기술 분야·연도 편향이 있습니다.

## AI 개선안 실험 (Claude, 2026-10-19)

채점: `scripts/grade_llm_runs.py` — 채점표 질문마다 Claude Sonnet 5.5가 예/아니오 판정, 가중치 합산, 3회 평균.
0844 만점 9, 0874 만점 8(청구항 1 실행 범위 밖인 기재불비 항목은 제외). 채점 사건이 2건뿐이라 순위는 참고용.

| 모델 · 설정 | 0844 | 0874 | 합계 | 응답 시간 |
| --- | --- | --- | --- | --- |
| qwen3:14b (로컬) | 1 | 0 | 1 | 1~2분 |
| qwen3:32b (s165) | 0 | 0 | 0 | 3~10분 |
| Sonnet 5.5 기본 (`retrieve`, v1) | 1 | 1 | 2 | 약 1.5분 |
| Sonnet + `elements` + v1 | 2 | 1 | 3 | 약 1.5분 |
| **Sonnet + `elements` + v2** (3회 실행 평균) | 4.3 | 1 | **5.3** | 약 1분 |
| Sonnet + `full` + v2 | 1 | 3 | 4 | 약 1분 |
| Opus 5.5 + `elements` + v2 | 4 | 3 | 7 | 약 3.5분 |
| **Opus 5.5 + `full` + v2** | 4 | 4 | **8** | 3~4분 |

원인과 조치:
- 기존 검색은 청구항 전체 한 문장으로만 질의해, 청구항을 되풀이하는 "과제의 해결 수단" 요약 문단만 뽑혔다.
  0844에서 실제 등록을 가른 [0077]~[0079]는 모델에 전달되지 않았다.
  → `IMPROVEMENT_SPEC_MODE=elements`(구성요소별 질의 + 인접 문단 병합, 청구항 재진술 문단 감점) / `full`(명세서 전체).
- v2 프롬프트(`IMPROVEMENT_PROMPT=v2`): "잘 알려진/단순 설계변경" 판단에는 상세 설명의 구체적 기술 수단·판단 단계로
  한정하라는 지침과, 평가셋 밖의 한국 사건 2건(10-2014-0003628, 10-2014-0002563)의 실패/등록 보정 예시.
  평가 대상 사건의 정답은 프롬프트에 넣지 않았다.
- Opus는 0844에서 출력이 16,000토큰 한도를 넘어 JSON이 잘렸다 → 스트리밍 + 32,000토큰으로 수정.
- 앱 기본값: Sonnet + `elements` + v2 (데모 속도). 품질 우선 시 `ANTHROPIC_MODEL=claude-opus-5-5`, `IMPROVEMENT_SPEC_MODE=full`.

한계: 평가 사건 2건, 채점자도 Claude. 채점표를 늘리고(재심사→등록 사건은 API만으로 작성 가능) 사람 검토가 필요하다.
